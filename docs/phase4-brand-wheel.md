# Phase 4: ブランド・ホイール(採用ブランド6軸評価)

Leggenda独自の採用ブランディング・フレームワーク「ブランド・ホイール」に基づき、
リードの相談申込時に、対象サイト(採用ページ・トップページ)から6軸24下位要素が
どこまで読み取れるかをAIで判定し、社内スタッフ・リード企業双方へ結果を通知する機能。

**社内向け情報です。Secret・Token・Cookie・APIキー・顧客の実名/実データはこの文書に
一切含めません。**

## 1. 6軸・24下位要素・Core Valueの位置づけ

`config/brand_wheel.php` の `axes` に定義。ヘキサゴン図の時計回りの並び順(上部から
時計回り)がそのまま配列のキー順になっている。

| 軸(表示順) | 英名 | グループ | 下位要素(4件ずつ) |
|---|---|---|---|
| 活動的魅力 | Will & Activity | 会社の魅力 | パーパス/展開事業・商品/PJ・新たな取組/社会貢献活動 |
| 資産的魅力 | Asset | 会社の魅力 | 知名度・評判/競争力・独自性/規模・影響力/オフィス・施設 |
| 経営スタイル | Personality | 会社との距離 | リーダーシップ/組織構造/会社の性格/重視する価値 |
| 就業環境 | Relationship | 会社との距離 | 同僚・先輩像/職場の雰囲気/物理的自由度/精神的自由度 |
| 情緒的便益 | Emotional Benefit | 仕事の魅力 | 誇りに思える/話したくなる/満足感/優越感 |
| 金銭的便益 | Financial Benefit | 仕事の魅力 | 給与水準/福利厚生/成長機会/雇用の安定性 |

**Core Value**は「6軸を貫く一言」であり、個々の軸の要約ではなく、しばしば視点の転換を
含む(教師データの例を参照)。ヘキサゴン図では中心の小さな六角形として、読み取れた場合は
実線、読み取れない場合は破線で描画する。

`quality_dimensions`(一貫性・信憑性・距離感・差別化・コーポレートブランドとの整合)は
6軸とは別の「全体の質を見る5つの観点」で、社内スタッフ向けメールにのみ含める
自由記述の所見(下記5節参照)。

## 2. 判定ロジック

**AIにstate(read/partial/unread)を一切出力させない。** AIが出力するのは
下位要素ごとの `matched_sub_elements: [{key, evidence}]`(該当する下位要素キーと、
それを裏づける原文からの抜粋)のみ。

判定(state)はすべてプログラム側(`BrandWheelAnalysisResponseParser`)が以下の手順で
計算する:

1. AIが申告した各 `matched_sub_elements` について、`evidence` が実際に
   `BrandWheelAnalysisInput`(採用ページ本文・トップページ本文・見出し・
   ナビゲーションラベル)に正規化後の部分一致で実在するか検証する。
   - 正規化は「空白の除去・全角半角の統一・引用符/ダッシュの統一」のみ。
     句読点の除去や部分文字列の再分割はしない(緩い正規化はAIの言い換えを
     「実在する記述」として通してしまうため)。
   - 実在しない場合はその下位要素キーだけを破棄する(軸全体は破棄しない)。
   - 破棄理由(`unknown_sub_element`/`empty_evidence`/`evidence_not_found`)を
     `discarded_sub_elements` に記録し、無言で切り捨てない。
2. 検証を生き延びた `matched_sub_elements` の件数から、
   `config('brand_wheel.state_thresholds')`(`overrides[axis] ?? default`)に
   従ってstateを計算する(`unread`/`partial`/`read`)。
3. 検証前にAIが申告した件数(`claimed_sub_element_count`)も保持する。これにより
   「AIはread/partialを自己申告したが検証で全滅した」という事実を、
   `claimed_sub_element_count` と最終的な `state` の比較から再構成できる
   (AIに"state"という集約ラベル自体を出力させない、より厳格な設計)。

Core Valueの `readable` も同様に、AIの自己申告ではなくevidenceの実在検証で決まる。

## 3. 閾値の初期値と根拠

`config('brand_wheel.state_thresholds')`:

```php
'default' => ['partial' => 1, 'read' => 2],
'overrides' => [],
```

検証を生き延びた下位要素が0件で`unread`、1件で`partial`、2件以上で`read`。軸によって
下位要素が同時に出現しやすいかどうかに構造的な偏りがある(資産的魅力・活動的魅力は
複数要素が同じ文章に自然に並びやすく、情緒的便益・経営スタイルは感情の言葉が2つ
揃うことが少ない)と想定されるため、軸ごとに上書きできる `overrides` を用意している。

**現時点でoverridesは未設定・初期値のまま。** 実サイトでの分布実測(本文書「5. 実測結果」
参照)が、実際のAPIキーが無い状態でまだ実施できておらず、調整の要否を判断できていない。
実測が可能になり次第、この節を更新すること(判定ロジックのコード自体は変更せず、
`config/brand_wheel.php` の値のみで調整する方針)。

`insufficient_input_min_total_chars`(既定200文字)の根拠は次節参照。

## 4. 送信を抑止する条件

### 4.1 `insufficient_input`(AIを呼ばない)

採用ページ本文+トップページ本文の合計文字数が
`config('brand_wheel.insufficient_input_min_total_chars')`(既定200文字)未満の場合、
AIを一切呼ばず `insufficient_input` として記録する。

理由: 「サイトに記述が読み取れなかった」(評価した結果、何も無かった)と「サイトの
記述を読みに行けなかった」(生HTML取得・ストレージ到達に失敗した等)を混同しないため。
後者を前者として扱うと、"6軸すべてunread"という体裁の整った(しかし中身の無い)結果が
正常な評価として送られてしまう。200文字という値は、実際の採用/トップページ本文が
通常数百〜数千文字あるのに対し、200文字未満で収まるのは「採用情報は現在ありません」
のようなプレースホルダーページか、取得・読み込み失敗で本文が実質空になっているケースが
ほとんど、という判断による初期値(実測未実施、調整可能性あり)。

### 4.2 `source_pages`(recruit_page / home_page)

各ページの取得状態を `read` / `absent`(行自体が無い、正常系)/
`unreadable`(行はあるがファイル実体が無い、ストレージ到達性の異常系)の3値で記録する。
`unreadable` はRenderの永続ディスク非共有等の障害と症状が一致するため、
`Log::error` で記録し運用上検知できるようにしている。

### 4.3 リード企業向けメールを送らない条件(いずれか1つでも該当したら送らない)

- `status !== 'success'`(`insufficient_input`/`error`/`pending`/`running`のすべてを含む)
- `source_pages.recruit_page === 'unreadable'`
- **6軸すべてunread(read+partialの合計が0)** ―― `status`が`success`であっても、
  「6軸すべて読み取れませんでした」という内容を社外に送ることはいかなる場合もしない。

社内スタッフ向けメールは、上記のいずれかに該当してリード向けを送らなかった場合も
必ず送信し、送らなかった理由を明記する。社内スタッフ向けメール自体は
`insufficient_input`/`error`を含め常に送る(評価の成否に関わらず、相談を受けたという
事実と理由を社内が把握できるようにするため)。

## 5. 社内スタッフ向け/リード企業向けの内容の違い

| | 社内スタッフ向け | リード企業向け |
|---|---|---|
| 目的 | 商談準備 | 関係構築・比較相談への誘導 |
| 内容 | 6軸の判定+根拠抜粋(全件)+品質所見(5観点)+留意事項+取得状況の診断情報 | 6軸の判定+要約+最小限の根拠抜粋(軸あたり最大1件) |
| ヘキサゴン画像 | あり(insufficient_input時は省略) | なし |
| 送信条件 | 常に送る(評価失敗・入力不足でも理由を明記して送る) | 4.3の条件をすべて満たした場合のみ |
| 自由記述(AI生成テキスト) | 品質所見・留意事項を含む | 一切含まない(evidence抜粋の引用+定型文言のみ) |

**理由**: 品質所見(一貫性・信憑性・距離感・差別化・整合)は、社内スタッフが商談で
使うための分析であり、そのままリード企業へ渡すものではない。またリード企業向けは
社外に出る文章のため、スコア・5段階評価・パーセンテージ・N/6の分数形式を一切使わず、
禁止語リスト(`config('brand_wheel.forbidden_phrases')`)による自動テストを最終防波堤
として持つ。リード企業向けのコンテンツ組み立て(`BrandWheelLeadEmailContentBuilder`)は
新規の自由文章生成を一切行わず、evidence検証済みの抜粋をテンプレート化するのみに
とどめている(禁止語混入という失敗モード自体を構造的に減らすため)。

リード企業向けメールには以下を必ず含める:
- 本評価はサイト上の記述から読み取れた範囲のものであり、貴社の実態を評価したもの
  ではないこと
- ブランド・ホイールは本来、グループインタビュー・口コミ・内定者や辞退者への
  インタビュー・説明会・SNS等、サイト以外の情報も併せて構築するものであること
  (下記6節も参照)
- AIが生成した文章であること
- 何を読んで判断したか(`source_pages` に基づく)

## 6. 既知の制約

**ブランド・ホイールは本来、サイト以外の素材(グループインタビュー、口コミ、
内定者・辞退者インタビュー、説明会、SNS等)も併せて構築するフレームワークである。
本システムはそのうちサイトの記述のみを見た部分的な読み取りに過ぎない。** この点は
社内スタッフ向け・リード企業向けのいずれのメールでも明示している。「サイトから
読み取れなかった」ことは「その会社にその魅力が無い」ことを意味しない、という区別を
常に維持すること。

## 7. 教師データ(few-shot実例)について

`config('brand_wheel.examples')` の教師データ(A社/B社/C社)は、依頼者から提供された
社内資料をもとに**既に匿名化済み**(社名→A社/B社/C社、固有の数値→定性表現、独自制度名→
一般名詞、地域名→「特定地域」等に加工済み)のものである。

**匿名化前のデータをこのシステムへ投入してはならない。** 露出範囲を広げるだけであり、
匿名化済みのものを使う方針で承認されている。教師データを更新する場合も、必ず
匿名化済みの状態で `config/brand_wheel.php` に反映すること。

$0.60/百万出力トークン)。

### 9.0 実測用CLIツール(非本番環境限定)

実測作業のために、`APP_ENV=production`では実行を拒否する2つのartisanコマンドを
用意している(2026-07-30追加、いずれも製品機能ではない ―― 本番の「1トークン1回」
の制限・相談ボタンの二重押下防止・input_hashによる再利用は一切変更していない)。

- **`php artisan lead:issue-test-session {self_url} {competitor_url?}`**:
  既存データを書き換えず、毎回新規にテスト用LeadSessionとトークンを発行し、
  診断を開始してワンタイムURLを標準出力へ表示する。リード情報はダミー値
  (メールアドレスは`@example.com`)。**出力にトークンが含まれるため、実行結果を
  ログファイルや報告に貼らないこと。**
- **`php artisan brand-wheel:run {website_analysis_id} [--force] [--output=<path>]`**:
  診断フロー全体を経由せず、既存のWebsiteAnalysisに対してブランド・ホイール分析
  だけを単体実行する。`--force`を指定すると、`input_hash`が一致する既存の
  `success`結果があっても再利用せずAIを再度呼ぶ(`GenerateBrandWheelAnalysisJob`の
  `forceRefresh`引数、production環境では強制的に無効化される)。`--output`を
  指定すると、パース済みの判定結果(6軸の`state`・`matched_sub_elements`・
  `discarded_sub_elements`・`claimed_sub_element_count`・`axis_state_counts`・
  `core_value`・使用モデル名・`prompt_version`・実測トークン数・所要時間)を
  JSONファイルへ書き出す。`BrandWheelAnalysisResult`モデル自身のカラムのみから
  組み立てており、このモデルにはリードの企業名・担当者名・連絡先を保持する
  カラムがそもそも存在しないため、出力にリードのPIIが混入する経路は無い
  (対象サイト本文のevidence抜粋は含まれる)。

**`--force`を付けずに同一サイトを複数回実行しても、安定性確認にはならない。**
2回目以降は`input_hash`の一致により結果が再利用され、AIを実際には1回しか呼んで
いないにもかかわらず「常に完全一致する」という見かけ上の結果になる。**さらに、
`--output`を使わずに同一`website_analysis_id`へ3回実行しても、`brand_wheel_
analysis_results`の対象行は毎回上書きされるため、比較する時点で1回目・2回目の
結果は失われている。** 下記9.1の安定性確認では、必ず`--force`と`--output`を
両方付けて、3回とも別々のファイルパスに出力すること。

### 9.1 実測の優先順位(この順序を必ず守ること)

実際のAPIキーが利用可能になった時点で、以下の順序で実施すること。**1が通らない
状態で3(閾値調整)を行っても意味が無い** ―― 同じ入力に対して結果が揺れるなら、
閾値をどう調整してもその調整自体が測定誤差に埋もれる。

1. **安定性(最優先、これが通らないとリリース不可)**: 以下の手順で実施する。

   ```
   php artisan lead:issue-test-session https://<自社サイト> https://<競合サイト>
   # 出力されたURLから website_analysis_id を確認する(URLそのものは
   # ログ・報告に貼らないこと)。

   php artisan brand-wheel:run {website_analysis_id} --force --output=/tmp/run1.json
   php artisan brand-wheel:run {website_analysis_id} --force --output=/tmp/run2.json
   php artisan brand-wheel:run {website_analysis_id} --force --output=/tmp/run3.json

   diff /tmp/run1.json /tmp/run2.json
   diff /tmp/run2.json /tmp/run3.json
   ```

   `--force`と`--output=<別ファイル>`を必ず両方付けて3回実行すること ―― `--force`
   が無ければ2回目以降はinput_hashの再利用で結果が固定され、`--output`が無ければ
   `brand_wheel_analysis_results`の対象行が毎回上書きされ、比較する時点で1回目・
   2回目の結果は失われている(いずれも見かけ上の「安定」を生むだけで測定として
   成立しない)。3つのJSONファイルを`diff`で比較し、6軸の`state`が完全に一致するか、
   `matched_sub_elements`のキー集合が一致するか、evidenceの抜粋箇所が一致するかを
   確認する。一致しない場合、それが最も重要な発見であり、揺れた軸と内容を具体的に
   報告すること。temperatureを下げても揺れる場合は、プロンプトか閾値の設計問題である。
2. **モデル比較(破棄率)**: 下記9.2節の手順で実施。
3. **10サイトのstate分布と閾値の妥当性**: 1・2が安定していることを確認した上で
   実施する。
4. **コスト・所要時間の実測**: 最後でよい(コスト自体は概算の時点で無視できる
   規模であることが分かっているため、優先度は最も低い)。

### 9.2 モデル比較(破棄率)の手順

**コスト概算が10件で数十円という規模である以上、`gpt-4o-mini`を選ぶ積極的な理由は
無い。** この処理は、日本語の本文から6軸に該当する記述を見つけ、原文を改変せずに
抜き出す作業である。小型モデルは要約・言い換えをする傾向があり、その場合evidence
検証で破棄されて結果が`unread`に倒れる ―― 原因はサイトの記述内容ではなくモデル側に
ある。軸の弁別(活動的魅力と資産的魅力の切り分け等)も、小型モデルほど曖昧になりやすい。

手順:
1. 同一の3サイトに対し、`gpt-4o-mini`と上位モデル(例: `gpt-4o`)の両方で評価を実行する。
2. 比較する指標:
   - evidence検証による破棄率(`discarded_sub_elements`のうち`evidence_not_found`
     理由の割合)
   - read/partial/unreadの分布
   - 軸ごとの`matched_sub_elements`の内容の妥当性(目視 ―― 該当する記述として
     挙げられた下位要素が、実際にその軸の趣旨に沿っているか)
3. **判断基準**: 破棄率が上位モデルで明確に低い場合、上位モデルを既定にする。
   コストは10件で数十円規模であり、選定基準にしない。
