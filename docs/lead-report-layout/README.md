# リード向け診断レポート レイアウト案（2026-08-03）

`resources/views/reports/lead-pdf.blade.php` をA4横のスライド構成に作り直すための
レイアウト案です。配色はレジェンダ・コーポレーションのコーポレートサイト
（https://www.leggenda.co.jp/）に合わせています。

## ファイル

| ファイル | 内容 |
| --- | --- |
| `report-layout-draft.html` | レイアウトのHTML。Bladeへ移植する元。 |
| `report-layout-draft.pdf` | 上をA4横で印刷したもの。見た目の確認用。 |
| `brand-wheel-framework.png` | 前置きページで使う説明図（分析結果に依存しない固定アセット）。 |
| `radar-sample.png` | レーダー図のサンプル画像。 |
| `leggenda-logo.png` | コーポレートロゴ。表紙・各ページ右下・最終ページで使用。 |

## 重要な前提

**数値・文章はすべてダミーです。** 実際の診断結果ではありません。全ページの右上に
「サンプル（ダミーデータ）」を入れてあります。本番テンプレートへ移植する際は、
この表示を必ず外してください。

**このPDFはChromiumで印刷したもので、dompdfの出力ではありません。** 見た目が
そのまま再現される保証はありません。移植後は必ず実際にdompdfでPDFを生成し、
目で確認してください。

6項目のチェックをすべて通過しています（CVD分離 ΔE 25.7、通常視 ΔE 37.7、
背景コントラストいずれも基準以上）。この2色を変更する場合は、必ず同じ検証を
やり直してください。目視で判断しないこと。

**グループ名から色名を外しています。** 元のスライドは「青／会社の魅力」
「緑／会社との距離」「赤／仕事の魅力」でしたが、配色をレジェンダに合わせた結果、

「仕事の魅力」としています。バックエンドが生成する文言（`BrandWheelComparisonSummaryComposer`）
には色名が含まれていないことを確認済みなので、この変更による不整合はありません。

## ロゴの扱い

`leggenda-logo.png`（512×94、白背景）を次の3箇所で使っています。

- 表紙: タイトルの上に中央配置（幅72mm）
- 各内容ページ: 右下に小さく（幅30mm）
- 最終ページ（ご相談）: 見出しの上に中央配置（幅60mm）

各ページ下部には **20mm の余白を確保** してあります。確保しないと、キーメッセージの
紺帯の上にロゴが重なります（実際に一度重なりました）。脚注も右端を 52mm 空けて
ロゴの手前で折り返すようにしています。**中身を増やす場合は、この余白を必ず維持し、
生成したPDFで重なりが無いことを目で確認してください。**

ロゴは `backend/resources/` 配下に静的アセットとして置き、base64 で埋め込んでください。

## フォントについて

レジェンダのサイトは **Noto Sans JP**（見出し weight 600）です。ただし
`PdfReportGenerator` のコメントにあるとおり、`fonts-noto-cjk` は TrueType Collection
(.ttc) でしか配布されておらず dompdf 側の対応が不安定なため、現状は IPAexゴシックを
埋め込んでいます。**この案でもフォントは IPAexゴシックのままにしてあり、配色と構成で
ブランドに寄せています。** Noto Sans JP を使いたい場合は、Google Fonts が配布する
単体 .ttf を Dockerfile で配置する必要があります（別タスク）。

## dompdfの制約（このHTMLで守っていること）

- flexbox・CSS grid は使えない。段組みはすべて `<table>` で組んでいる
- `clip-path` は使えない。スライドにある六角形のラベルは矩形で代用している
- `box-shadow` は使わない。`border-radius` も最小限にとどめている
- 画像は `<img src="data:image/png;base64,...">` で埋め込む
  （このドラフトでは読みやすさのため外部参照にしている）

## 3・4ページ目「自社/競合サイトの分析結果」の要件

`resources/views/reports/partials/lead-pdf-brand-wheel-page.blade.php` に
共通パーシャル化してあり、主体（自社/競合）を差し替えるだけで完全に同じ
形式・レイアウトになります。片方だけ直して食い違う事故を防ぐため、
レイアウトを変える場合は必ずこのパーシャル1箇所を直してください。

- 合計件数を「N / 24項目」で大きく出す。系列色の色見本を添える。
  この数字がこのページの主役（このページは自社/競合いずれか単独の
  データのみを表示する ―― 相手側の件数・レーダー系列は出さない）
- 各軸に `max_count` 個の四角を置き、`matched_count` 個だけ塗る。
  **四角の数は `max_count` から生成すること。4を固定値で書かない**
- この四角は「壊れて出ていない」のか「調べた結果0件」なのかを区別するための表示。
  省略しないこと
- 0件のセルの文言は「該当する記述は見つかりませんでした」。
  「読み取れた内容はありません」は使わない（内容が無い会社、と読める）
- 軸セルの高さは 38mm 確保する
- 文言は「収集した情報から想定されるキーメッセージ」「AI解析による
  候補者に与える印象」を使う（旧「キーメッセージ」「AI解析による印象」から
  変更、2026-08-08）
- 印象（impression）は2〜4件の短いフレーズの箇条書きで示す。評価・提言を
  含めず、候補者が受け取る印象を列挙するだけにすること（下位要素の判定
  結果と重複した提言調にしない）。evidence本文は引き続き出さない

## 5ページ目「○△－の対比表」の要件

3グループを横に並べ、各項目の記述有無を ○／△／－ の3値で示す。

- **○×は使わないこと。** ×は正解・不正解の記号であり、×が並ぶと採点で
  落ちたように見える。2ページ目の「読み取れなかった項目は、その魅力が
  無いという意味ではありません」と矛盾する
- 判定は必ずプログラム側（`BrandWheelSubElementComparisonComposer`）で行う。
  **AIに3段階を判定させないこと** ―― AIの引用を原文照合で検証する
  仕組みの外側に検証できない判断を入れないため
    - ○: 本文からの引用が原文照合を通った（`matched_sub_elements`）
    - △: 見出し・リンクラベルのみを根拠に破棄された
      （`discarded_sub_elements` の `reason==='label_only_evidence'`）
    - －: それ以外（AIが該当なしと判定/evidence_not_found/empty_evidence/
      duplicate_evidence）。根拠が実在しないものを△に格上げしないこと
- 凡例（○△－の意味）は必ず表の近くに置く
- 24項目は config の定義順で出す。表示順をコードに直書きしない
- 比較サイトが無い場合は「比較」列を落とし、自社の列だけにする
- 合計（○の数）は3・4ページ目の合計と必ず一致させる。同じソースから算出すること
  （△は合計に含めない。参考件数として別行に出す）
- 冒頭に自社×競合を重ねたレーダー図を置く。3・4ページを自社単独・競合単独に
  分けたことで、視覚的な対比はこのページにしか無いため。競合が読み取れない
  場合は出さない

## 6ページ目「改善提案」の要件

**ブランド・ホイール起点であること。** 技術的な指標から作らないこと。

- グループごとの 自社／競合 件数バーを出し、差が最大の領域を特定する
- その領域から3項目を、**比較サイトの実際の evidence つき**で提示する
- 「候補者が知ろうとすること」は config の下位要素定義文を流用
- 領域の選択・3項目の選択は**決定的な規則**で行う。同点規則も明文化すること
- 選定ロジックは○/△を区別しない（△は未該当扱い） ―― 自社△かつ競合○の
  項目も引き続き改善提案の候補に含める。ここを変えると選定結果が大きく
  動くため変更しないこと（2026-08-08時点でのユーザー判断）
- 橋渡しの一文「なお、これらを『サイトに書き足す』ことで解決するとは
  限りません。実態はあるのに伝えられていないのか、まだ言葉になって
  いないのか ―― その切り分けについては最終ページをご覧ください。」を消さない
- 技術的提案ブロック（画像・速度・フォーム等）は2026-08-08に削除した
  （4観点の測定結果ページを削除したのに技術的提案だけ残すのは整合が
  取れないため）

### 競合が無い（または読み取れない）場合（2026-08-10追加）

旧実装は「比較サイトが無いため、領域ごとの比較はご用意できません。」の
1行だけで、ページの大半が空白になり営業資料として成立しなかった
（ユーザー指摘）。**ページを消すのではなく、競合を使わない中身に差し替える。**

- `BrandWheelImprovementFocusComposer::composeSelfOnly()`が唯一の情報源
  （`compose()`とは別メソッド、競合のevidenceを一切参照しない）
- **グループ選定**: 3グループそれぞれで自社の「－」（`self_state==='none'`）の
  件数を数え、最多のグループを選ぶ（同点はconfig順）。選んだグループが
  「－」も「△」も0件（＝8/8で○のみ）の場合は、「－」が次に多いグループへ
  移る
- **3項目選定**: 選んだグループ内の「－」項目をconfig順に並べ、3件に
  満たない場合は同グループの「△」項目（config順）で埋める（－が優先、
  △は「見出し・リンクラベルのみで具体性が無い」ため次点）
- 件数バーは自社のみ（競合の赤いバーは出さない）
- カードは「比較サイトの記述」ブロックを持たない。「御社のサイト」欄の
  文言は選定理由で分ける（－由来は「記述が見つかりませんでした」、
  △由来は「見出し・リンクラベルのみで、具体的な記述は見つかりません
  でした」―― 対比表ページの△の定義と一貫させるため、一律の文言にしない。
  2026-08-10、ユーザー承認）
- リード文・橋渡しの一文は競合ありの版と文言を変える（config
  流用ではなく固定文言、`lead-pdf.blade.php`/`WordReportGenerator.php`参照）
- **ページを出さない条件**: 自社24項目すべてが○の場合のみ`null`を返し、
  呼び出し側はこのページ自体を省略する（実運用ではまず起きないが、
  白紙ページを作らないための保険。発生時はログに記録する）

## レーダー図について

`App\Services\BrandWheel\BrandWheelRadarSvgBuilder` が生成します。既存の
`BrandWheelHexagonSvgBuilder` は「1サイト分の6扇形」で、これとは別物です
（流用していません）。

幾何計算は `frontend/src/features/lead/lead-brand-wheel.tsx` の
`wheelPoint()` / `axisRatio()` と同じ式です。

- 0時方向を起点に時計回り
- 半径は `matched_count / max_count`
- `max_count` が 0 の軸は 0 として扱わず、点を打たない
- 目盛りリングは `max_count` 分。テンプレートに 4 や 5 を固定値で書かない
- 自社 `#3A3FC0` / 競合 `#E95446`、`fill-opacity` 0.16、点は白フチ付き
- 競合の分析が success でない場合は自社の面だけを描く

2026-08-08、7ページ構成への再編で用途が3種類に増えました。
`ReportViewModelBuilder::buildRadarPng()` が1メソッドで生成を切り替えます。

1. 3ページ目（自社単独）: `build($selfAxes, null, primaryColor: 自社色)`
2. 4ページ目（競合単独）: `build($competitorAxes, null, primaryColor: 競合色)`
   ―― `build()` は常に第1引数（主系列）を`$primaryColor`（既定は自社色）で
   描くため、競合単独ページでは明示的に競合色を渡すこと。渡し忘れると
   競合のデータが自社色（青）で描かれる
3. 5ページ目（対比表、自社×競合の重ね図）: `build($selfAxes, $competitorAxes)`
   ―― 競合が読み取れない場合はこの図自体を出さない（3・4ページ単独図の
   重複表示になるだけで、対比表ページで新たに示す情報が無いため）

PNG化は既存の `BrandWheelHexagonRenderer` をそのまま使います
（rsvg-convert・不透過背景・IPAexゴシック）。新しいラスタライズ経路は作っていません。
PNGが生成できなかった場合は図を省略し、軸ごとの件数の表だけで成立させます
（画像の失敗がレポート生成全体を止めてはいけない、という既存メールと同じ方針）。

## 既知の限界

**改善提案ページの競合根拠に「案内文」が混じることがある。** evidence実在検証
（`BrandWheelAnalysisResponseParser`）は原文に文字列が実在するか・見出しや
リンクラベルだけの引用でないか（`label_only_evidence`）は判定するが、「その
下位要素の内容そのものを述べた文か」までは判定していない。たとえば
「SmartHRのバリューがプロダクト開発の文脈でどのように体現しているかを
ご紹介します。」のような、本文中に実在し・見出しでもリンクラベルでもない
が、内容そのものではなく「この先で紹介します」という案内文は、現状の検証
をすり抜けて matched として残る（2026-08-09、実PDF確認で発見）。

○△－対比表ページは24項目中の1つなので目立ちにくいが、**改善提案ページは
最大3件しか出さないため、そのうち1件がこの案内文だと相対的に目立つ**
（2026-08-09、ユーザー指摘）。今回は対処していない。対処する場合はAIへの
プロンプト指示（「これから紹介します」等の前置き文を根拠にしない）を追加
するか、パーサ側に案内文パターンの簡易フィルタを追加する方向が考えられる
が、後者は「何が案内文か」の恣意的な判定基準を増やすことになるため、
安易に追加しない。

**dompdfのtable-layout:fixedは、幅の広い折り返しテキストを持つtdを
最終列に置くと列幅指定を無視することがある。** ○△－対比表ページの
レーダー+凡例の横並び実装で、凡例(折り返しテキスト、165mm)をレーダー
(92mm)の右側=表の最終列に置いたところ、`table-layout:fixed`で列幅を
明示していても最終列がページ右端(297mm)を大きく超えて描画される不具合を
実PDF確認した（2026-08-10）。原因は特定できていないが、列の並びを
逆にする（幅の広い折り返しテキストのtdを最終列にしない）ことで解消した。
このファイル内で同種の横並びレイアウトを追加する際は、幅の広いテキスト
列を最終列に置かないこと。
